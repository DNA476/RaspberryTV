# Клавиатура для сторонних приложений — следующий этап

Разбор от 2026-09-08. Это план реализации, общесистемного ввода в текущем коде нет.
Ввод URL нового браузера использует редактор оболочки и не решает ввод в поля сайта,
поиск Kodi или ввод на удалённом компьютере через Moonlight.

## Что уже есть

- `qml/Main.qml`: редактор текста/пароля и клавиши на экране. Они меняют локальный
  `TextArea` или `TextField`; текст передаётся в `Bridge._save_editor` при сохранении.
- `InputReader`: чтение evdev, навигация, короткий/длинный PS, Options. Устройства
  сейчас не захватываются эксклюзивно, поэтому само приложение может также получать
  исходные события геймпада. Для клавиатуры поверх Kodi это нужно проверить отдельно.
- `Applications`: учёт запущенных приложений и их X11-окон по процессу/потомкам,
  включая XRes для окон без PID. Целевое окно следует брать отсюда, а не по заголовку.
- `__main__.surface`: быстрое меню получает фокус Qt; страница `application`
  скрывает оболочку. Для браузерного URL меню скрывается до активации Chromium.

## Первый вариант для реализации

1. Ручной пункт **Клавиатура** в быстром меню при активном локальном приложении.
   Сначала ограничить поддерживаемые цели Chromium и Kodi; Moonlight проверять отдельно.
2. Сохранить приложение, его процесс и окно при открытии клавиатуры. Показать,
   куда будет отправлен текст. Не менять цель вслед за случайной сменой окна.
3. Переиспользовать текущую раскладку и навигацию. Сначала вводить и исправлять
   текст в буфере оболочки, затем отдельной кнопкой отправлять его в приложение.
   Дать варианты **Вставить** и **Вставить и Enter**, не подтверждать форму автоматически.
4. Перед отправкой скрыть клавиатуру, восстановить выбранное окно и проверить
   его фокус и жизнеспособность. При потере цели прекратить ввод и вернуть редактор.
   Не использовать буфер обмена как скрытое хранилище паролей; не записывать текст
   в настройки, аргументы команд и журналы. При закрытии очищать буфер.
5. Проверить способ временно отделять навигацию по клавиатуре от исходных событий
   геймпада в приложении. При выходе, потере устройства и завершении оболочки ввод
   должен освобождаться. Не вводить глобальный постоянный захват устройств.
6. Только после ручного сценария исследовать автоматический вызов по доступным
   сигналам о фокусе текстового поля; сохранить ручной вызов для неподдерживаемых полей.

Предполагаемый транспорт — XTEST через существующий X11-сеанс. В документации
[xdotool](https://github.com/jordansissel/xdotool/blob/main/xdotool.pod#sendevent-notes)
указано, что адресованные окну события XSendEvent могут игнорироваться приложениями.
Поэтому нельзя считать `xdotool key --window …` универсальным решением.
Проверка активного окна сама по себе не исключает смену фокуса посреди ввода;
до поддержки парольных полей это ограничение необходимо решить и проверить.

## Проверка

На ПК можно проверить показ/отмену, все клавиши и раскладки, очистку буфера,
сохранение целевого окна, отказ при закрытии приложения и порядок команд.
Для доставки событий нужен отдельный Linux-сеанс X11 хотя бы с тестовым полем;
моки этого не подтверждают. На Pi затем нужны реальный Chromium/Kodi, DualSense
USB/Bluetooth, символы на кириллице, исправление текста, Enter, парольные поля,
выход по PS/Options и отсутствие двойной обработки кнопок.
